# INC-001: respuesta 500 ante firma JWT inválida

| Campo | Valor |
|---|---|
| Estado | Abierta; reproducida en dos solicitudes |
| Fecha | 09/11/2026, America/Bogota |
| Caso / riesgo | CT-R03-03 / R03 |
| Endpoint | GET https://dummyjson.com/auth/me |
| Severidad propuesta | Media: manejo incorrecto de error; sin acceso al perfil en estas observaciones |
| Prioridad de atención | Alta por afectar un caso P1 de autenticación |
| Responsable de corrección | Proveedor de DummyJSON; fuera del control del equipo |
| Ejecutor / analista | Ejecución e inspección HTTP asistida; sin firma de aprobación externa |

## Precondiciones

Obtener un accessToken auténtico con la cuenta pública de demostración. Cliente sin CookieJar ni cookies; usar solo Authorization: Bearer. El token original permite /auth/me en el control positivo CT-R03-01.

## Reproducción

1. POST /auth/login con credenciales públicas válidas.
2. Separar el JWT en sus tres segmentos.
3. Cambiar únicamente el primer carácter del segmento de firma por otro carácter base64url.
4. GET /auth/me con el token alterado y sin cookies.

## Esperado y observado

Esperado del caso: rechazo 401 o 403, sin perfil. Observado dos veces: **HTTP 500** con JSON `{"message":"invalid signature"}`. No se observaron campos id o email de un perfil en esas respuestas. El rechazo no constituye un bypass; el defecto registrado es la clasificación HTTP de un fallo de autenticación.

## Evidencia y retest

Primera corrida: ver el caso CT-R03-03 dentro del primer archivo auto en evidencias. El ejecutor v0.1 lo clasificó inicialmente como Bloqueado por una regla general para 5xx. Se preserva ese registro. Tras corregir la clasificación del cliente, se repitió sin cambiar el criterio 401/403: volvió a responder 500 y se registró Fallido. [Registro y archivos concretos](registro-ejecucion.md).

No se modificó el backend de DummyJSON y no se declara corregido el defecto. Una futura verificación debe repetir el caso y los controles válido, ausente y expirado.
